ServiGo Case Study

1. One-line Impact Summary

ServiGo unified customer booking, technician dispatch, admin governance, and support-led operations into a single role-secure platform for appliance service businesses.

2. Problem Statement

Local service teams often run on fragmented tools (calls, spreadsheets, chat), causing missed follow-ups, delayed assignments, poor visibility, and inconsistent customer experience.

3. Product Vision

Create an end-to-end operational product for appliance servicing where every role can execute tasks through controlled permissions and a clear service lifecycle.

4. User Personas & Responsibilities

  • Customer: Browse services, create bookings, track timeline and notifications.
  • Technician: Maintain profile, manage availability, accept/reject/complete jobs.
  • Admin: Technician approvals, service control, booking/user governance.
  • Support Desk: Caller bookings, customer history lookup, operational assistance.

5. Information Architecture

  • Shared: Auth, role routing, notifications, session handling.
  • Customer: Service catalog, booking flow, timeline, notification center.
  • Technician: Assigned jobs, skills, availability, action lifecycle.
  • Admin: Service management, booking control, technician/user management.
  • Support: Caller booking, customer 360 search by mobile/email, history view.

6. System Architecture

Frontend: React (CRA), React Router, CSS

Backend: Node.js, Express

Database: MongoDB (Mongoose)

Security: JWT auth + role-based access control

Notifications: In-app events + SMS hook logic

Password reset: Firebase OTP flow (without visible captcha in UI)

Open Architecture Diagram

7. Key Workflows

  • Customer booking: Browse -> book -> timeline tracking -> notifications.
  • Technician lifecycle: Accept/reject -> execute -> complete job.
  • Admin approval: Service Desk-created technician still requires admin approval.
  • Caller booking: Mobile lookup/new customer flow with optional time input.

8. My Responsibilities

  • Designed multi-role flows and role-responsibility boundaries.
  • Built frontend route architecture and protected views.
  • Implemented Express APIs and role guard middleware.
  • Modeled Mongo schemas for booking lifecycle and operations.
  • Implemented session persistence controls and UX messaging.

9. Technical Decisions & Trade-offs

  • Used CRA for rapid dashboard iteration (trade-off: no SSR benefits).
  • JWT for stateless auth scalability (trade-off: explicit revocation strategy needed).
  • MongoDB for evolving role/booking entities (trade-off: strict service-level validation required).

10. Security & RBAC Design

  • JWT validation and role checks at API layer.
  • Protected role-based pages on frontend.
  • Support cannot block users (admin-only action).
  • Technician activation gated by admin approval workflow.

11. Challenges & Solutions

  • Complex role navigation solved with role-aware route maps.
  • Caller booking edge-cases solved with mobile-first customer lookup.
  • Operational ambiguity solved with explicit success feedback messaging.

12. UI/UX Improvements

  • Role-wise navigation behavior for faster task completion.
  • Navbar/home/dashboard flow improvements for operational clarity.
  • Fixed Call Now CTA across non-admin pages for immediate support access.
  • Theme handling with light/dark mode for usability preference.

14. Lessons Learned

  • API-level permission checks are non-negotiable for multi-role systems.
  • Support tooling is as important as customer-facing UI.
  • Clear operational feedback states reduce internal errors significantly.

15. Future Roadmap

  • Smart dispatch recommendation using skills + workload context.
  • Audit logs for sensitive support/admin operations.
